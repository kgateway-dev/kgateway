## Background
Kgateway testing leverages the [Ginkgo](https://onsi.github.io/ginkgo/) test framework. As outlined in the linked documentation, Ginkgo pairs with the [Gomega](https://onsi.github.io/gomega/) matcher library to provide a BDD-style testing framework. For more details about how to write tests, check out our [writing tests docs](writing-tests.md).

## Common Make Targets
There are a few common make targets that can be used to run tests

### test
The `test` target provides a wrapper around invoking `ginkgo` with a set of useful flags. This is the base target that is used by all other test targets.

### test-with-coverage
Run tests with coverage reporting using Ginkgo.

### go-test
Run tests using `go test` directly. This is the primary target used by CI for running tests. Use the `TEST_PKG` environment variable to specify which packages to test, and `GO_TEST_USER_ARGS` to pass additional arguments like `-run` regex patterns for test selection.

### go-test-with-coverage
Run tests with coverage reporting using `go test`. This is used by CI for unit tests

## Coverage

CI combines unit coverage with coverage from the instrumented kgateway controller in Kubernetes e2e tests. Each e2e shard uploads `coverage-e2e-<cluster-name>/cover.out`; unit tests upload `coverage-unit/cover.out`. Matching blocks are merged, so a statement exercised by any test counts as covered without counting that statement more than once. Conformance and other suites are not automatically included.

The total measures **statement coverage**, not branch coverage. Patch coverage approximates coverage of added or changed lines using executed statement blocks; it is not precise line coverage and does not establish that both outcomes of a conditional were tested.

Unit coverage instruments all packages with `-coverpkg=./...`, so calls from tests in another package count toward the package they exercise. For example, setup tests contribute coverage to the proxy syncer.

The `Test Coverage` job publishes a summary and a `coverage-html` artifact containing `coverage.html` and `cover.merged.out`. It enforces a 55% combined statement coverage minimum when e2e succeeds. File, package, and patch minimums are currently disabled. Validation excludes generated protobuf files, `zz_generated*.go`, `test/`, and `hack/`, as configured in [test_coverage.yml](/test_coverage.yml). The summary total and HTML report apply the same configured exclusions as validation.

If e2e fails or the wait times out, CI reports the available coverage and skips threshold enforcement. A successful e2e workflow does not guarantee every shard supplied a profile: missing coverage uploads only produce warnings.

To generate and view unit coverage locally, run from the repository root:

```bash
make unit-with-coverage
make view-test-coverage
```

Separate unit and e2e HTML reports are not generated by CI. To render e2e-only coverage, download and extract the `coverage-e2e-*` artifacts from the same run under `_output/coverage/`, retaining one directory per artifact, then run:

```bash
profiles="$(find _output/coverage/coverage-e2e-* -name cover.out | sort | paste -sd, -)"
make html-test-coverage COVERAGE_PROFILES="$profiles"
```

Open `_output/coverage.html` to view the result. `COVERAGE_PROFILES` accepts any comma-separated list of profiles, so include the unit profile to produce a combined report. Use the matching source checkout when rendering downloaded profiles. Add `COVERAGE_BASE=origin/main` to report patch coverage against that locally available ref; `COVERAGE_MIN_PATCH` defaults to `0`.

Additional jobs in the unit workflow can contribute a `coverage-<name>` artifact containing `cover.out`, provided the coverage job waits for them through `needs`. Separate workflows require an explicit download step, as used for e2e.

## Environment Variables
Shared environment variables that can be used to control the behavior of the tests are defined in [env.go](/test/testutils/env.go). Below are a few that are commonly used:

#### GINKGO_USER_FLAGS
The `GINKGO_USER_FLAGS` environment variable can be used to pass flags to Ginkgo. For example, to run the tests with very verbose output, you can run:
```bash
GINKGO_USER_FLAGS="-vv" make test
```
*For the full set of available Ginkgo flags, check out the [documentation](https://onsi.github.io/ginkgo/#ginkgo-cli-overview)*

#### TEST_PKG
The `TEST_PKG` environment variable can be used to run a specific test suite. For example, to run the `test` test suite, you can run:
```bash
TEST_PKG=test make test
```

If you would like to run multiple test suites, you can separate them with a comma:
```bash
TEST_PKG=package1,package2 make test
```

If you would like to recursively run tests in a directory, you can use the `...` syntax:
```bash
TEST_PKG=test/... make test
```

#### GO_TEST_USER_ARGS
The `GO_TEST_USER_ARGS` environment variable can be used to pass additional arguments to `go test` when using the `go-test` target. For example, to run specific tests matching a regex pattern:
```bash
TEST_PKG=./test/e2e/tests GO_TEST_USER_ARGS="-run ^TestKgateway$" make go-test
```

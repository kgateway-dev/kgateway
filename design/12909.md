# EP-12909: API Key Authentication for kgateway Traffic Policies

* Issue: [#12909](https://github.com/kgateway-dev/kgateway/issues/12909)

## Background

API key authentication is a common security mechanism for API gateways, allowing clients to authenticate using API keys provided in HTTP headers. Currently, kgateway supports API key authentication in agentgateway policies, but this functionality is missing from the kgateway TrafficPolicy API which uses Envoy as the data plane proxy.

This EP proposes adding API key authentication support to kgateway TrafficPolicy, enabling users to secure their routes with API key validation. The implementation will leverage Envoy's native API key auth filter (`envoy.filters.http.api_key_auth`) for efficient authentication at the proxy level.

## Motivation

### Goals

- Add API key authentication support to `TrafficPolicy` resources for kgateway data plane
- Support flexible API key storage in Kubernetes Secrets with optional metadata
- Enable per-route API key authentication configuration
- Provide security features like hiding API keys from upstream services
- Support strict authentication mode (requests without valid API key are rejected)
- Allow configuration of custom header names for API keys
- Maintain consistency with existing agentgateway API key authentication API

### Non-Goals
- Metadata header forwarding to upstream (initial non-goal)
  - Envoy's native API key auth filter (`envoy.filters.http.api_key_auth`) does not natively support forwarding metadata from API keys as headers to upstream services
  - Implementing this would require a custom multi-filter approach such as the following:
    - API key auth filter for validation
    - Header-to-metadata filter to extract client information
    - Lua filter to parse and inject metadata headers (e.g., `x-role`, `x-tenant`) based on API key metadata
  - Alternatively, this could be implemented using ext_authz with a custom auth service, but that adds deployment complexity and latency
  - This feature may be considered in a future EP if there is sufficient demand

## Implementation Details

### API Changes

The API key authentication configuration is added to `TrafficPolicySpec` in `api/v1alpha1/traffic_policy_types.go`:

```go
// APIKeyAuthentication authenticates users based on a configured API Key.
// +optional
APIKeyAuthentication *APIKeyAuthentication `json:"apiKeyAuthentication,omitempty"`
```

The `APIKeyAuthentication` type is defined in `api/v1alpha1/shared_types.go` as a shared type between agentgateway and kgateway policies. The struct was originally implemented for agentgateway policies and has been extracted to shared types to enable reuse in TrafficPolicy:

```go
// +kubebuilder:validation:Enum=Strict;Optional
type APIKeyAuthenticationMode string

const (
	// A valid API Key must be present.
	// This is the default option.
	APIKeyAuthenticationModeStrict APIKeyAuthenticationMode = "Strict"
	// If an API Key exists, validate it.
	// Warning: this allows requests without an API Key!
	APIKeyAuthenticationModeOptional APIKeyAuthenticationMode = "Optional"
)

// +kubebuilder:validation:ExactlyOneOf=secretRef;secretSelector
type APIKeyAuthentication struct {
	// Validation mode for api key authentication.
	// +kubebuilder:default=Strict
	Mode APIKeyAuthenticationMode `json:"mode"`

	// headerName specifies the name of the header that contains the API key.
	// If not specified, defaults to "api-key".
	// +kubebuilder:default=api-key
	// +kubebuilder:validation:MinLength=1
	// +kubebuilder:validation:MaxLength=256
	HeaderName *string `json:"headerName,omitempty"`

	// hideAPIKey removes the API key from the request before forwarding upstream.
	// This applies to the header specified in headerName.
	// +kubebuilder:default=false
	HideAPIKey *bool `json:"hideAPIKey,omitempty"`

	// secretRef references a Kubernetes secret storing a set of API Keys.
	SecretRef *corev1.LocalObjectReference `json:"secretRef,omitempty"`

	// secretSelector selects multiple secrets containing API Keys.
	SecretSelector *SecretSelector `json:"secretSelector,omitempty"`
}

type SecretSelector struct {
	// Label selector to select the target resource.
	MatchLabels map[string]string `json:"matchLabels"`
}
```

### Secret Format

API keys are stored in Kubernetes Secrets with the following format:

**Simple format (string value):**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-keys
stringData:
  user: "real-key"
```

**JSON format with metadata:**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-keys
stringData:
  user: |
    {
      "key": "real-key",
      "metadata": {
        "role": "admin",
        "tenant": "acme"
      }
    }
```

The secret key name (e.g., `user`) becomes the client identifier that can be used for authorization or logging purposes. Note that while the JSON format supports metadata fields, this metadata is not currently forwarded to upstream services per the non-goal described earlier.

### Envoy Configuration

The implementation will configure Envoy's API key auth filter (`envoy.filters.http.api_key_auth.v3.ApiKeyAuth`):

```json
{
  "name": "envoy.filters.http.api_key_auth",
  "typed_config": {
    "@type": "type.googleapis.com/envoy.extensions.filters.http.api_key_auth.v3.ApiKeyAuth",
    "credentials": [
      {
        "key": "real-key",
        "client": "user"
      }
    ],
    "key_sources": [
      {
        "header": "X-API-KEY"
      }
    ],
    "forwarding": {
      "header": "x-client-id",
      "hide_credentials": true
    }
  }
}
```

### Translator Implementation

The translator will need to:

1. **Process TrafficPolicy with API key authentication:**
   - Extract API key configuration from `TrafficPolicySpec`
   - Resolve secrets using `secretRef` or `secretSelector`
   - Parse secret entries (both string and JSON formats)
   - Build Envoy API key auth filter configuration

2. **Secret Resolution:**
   - For `secretRef`: Fetch single secret by name
   - For `secretSelector`: Fetch all secrets matching labels in the policy namespace
   - Handle missing secrets with appropriate error reporting

3. **Filter Configuration:**
   - Map API keys from secrets to Envoy `credentials` format
   - Configure `key_sources` based on `headerName`
   - Set `forwarding.hide_credentials` based on `hideAPIKey`
   - Apply per-route configuration for route-level policies

4. **Mode Handling:**
   - `Strict` mode: Reject requests without valid API key (default Envoy behavior)
   - `Optional` mode: Not initially supported
     - The API includes `Optional` mode for consistency with agentgateway, but initial implementation will only support `Strict` mode
     - Envoy's API key auth filter doesn't natively support optional mode, and implementing it would require additional complexity
     - Support for `Optional` mode may be added in a future update if there is sufficient demand

### Example Usage

**TrafficPolicy targeting an HTTPRoute:**
```yaml
apiVersion: gateway.kgateway.dev/v1alpha1
kind: TrafficPolicy
metadata:
  name: api-key-auth
  namespace: default
spec:
  targetRefs:
  - name: my-api-route
    kind: HTTPRoute
    group: gateway.networking.k8s.io
  apiKeyAuthentication:
    mode: Strict
    headerName: "x-api-key"
    hideAPIKey: true
    secretSelector:
      matchLabels:
        type: api-keys
```

**Secret with API keys:**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-keys
  namespace: default
  labels:
    type: api-keys
stringData:
  user: |
    {
      "key": "real-key",
      "metadata": {
        "role": "admin",
        "tenant": "acme"
      }
    }
  service: "service-key-123"
```

### Configuration

No additional configuration changes are required. The feature uses existing Kubernetes Secret resources and follows standard TrafficPolicy attachment patterns.

### Plugin

The implementation will be added to the traffic policy plugin system:

- **Location**: `internal/kgateway/extensions2/plugins/trafficpolicy/`
- **Responsibilities**:
  - Process `APIKeyAuthentication` field from TrafficPolicy
  - Resolve and parse secrets
  - Generate Envoy API key auth filter configuration
  - Apply filter to appropriate routes/listeners

### Controllers

No new controllers are required. Existing TrafficPolicy controllers will handle the new field automatically through the standard reconciliation process.

### Translator and Proxy Syncer

The translator will need updates to:

1. **Filter Chain Construction:**
   - Add API key auth filter to HTTP filter chain when API key authentication is configured
   - Position filter appropriately in the chain (before routing, after request ID)

2. **Route Configuration:**
   - Support per-route API key auth configuration via `ApiKeyAuthPerRoute`
   - Handle policy attachment at Gateway, Listener, and Route levels

3. **Secret Watching:**
   - Watch for secret changes and update Envoy configuration accordingly
   - Handle secret deletion gracefully

### Reporting

Status reporting should include:

- Validation errors for missing or invalid secrets
- Errors for malformed API key entries in secrets
- Warnings for duplicate API keys across multiple secrets

## Alternatives

### Alternative 1: Use ext_authz Instead of Native API Key Filter

**Pros:**
- More flexible (can support metadata header forwarding)
- Consistent with existing ext_authz infrastructure
- Supports complex authorization logic

**Cons:**
- Requires external auth service
- Higher latency (external call)
- More complex deployment
- Less efficient than native filter

**Decision:** Use native Envoy API key auth filter for better performance and simpler deployment.

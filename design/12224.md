# EP-12224: Correct Status on Gateway/Listeners

* Issue: https://github.com/kgateway-dev/kgateway/issues/12224

## Background

When the IR translator is translating a Gateway, the individual Listeners are translated in a loop, and may have run into issues that prevent them from being translated and propagated to the data plane. We want this state to be captured in the status and conditions, specifically The `Accepted` and `Programmed` types

* [ListenerConditionAccepted](https://github.com/kubernetes-sigs/gateway-api/blob/release-1.3/apis/v1/gateway_types.go#L1156-L1183)
* [ListenerConditionProgrammed](https://github.com/kubernetes-sigs/gateway-api/blob/release-1.3/apis/v1/gateway_types.go#L1261-L1286)
* [GatewayConditionAccepted](https://github.com/kubernetes-sigs/gateway-api/blob/release-1.3/apis/v1/gateway_types.go#L975-L999)
* [GatewayConditionProgrammed](https://github.com/kubernetes-sigs/gateway-api/blob/release-1.3/apis/v1/gateway_types.go#L898-L926)

## Motivation

To have Gateway statuses and Listener subresource statuses be accurate and consistent.

## Goals

* To have Gateway statuses and Listener subresource statuses be accurate and consistent.


## Non-Goals
* Identifying the specific confitions that cause a Listener not to be Accepted or Programmed.
* Consolidating status types other than Programmed and Accepted, though the solution implemented should be easily extensible.

## Implementation Details

When the IR translator [translates a Gateway](https://github.com/sheidkamp/kgateway/blob/577334887c23e4b4d53c6d39b24487c6be05abae/internal/kgateway/translator/irtranslator/gateway.go#L44-L66), it calls [CopmuteListener](https://github.com/sheidkamp/kgateway/blob/577334887c23e4b4d53c6d39b24487c6be05abae/internal/kgateway/translator/irtranslator/gateway.go#L79) for each listener. ComputeListener returns an Envoy Listener and a Route Configuration, and if the listener is nil or does not contain a filter chain, the listener is not added to the translation output.

Assumptions about Listener Statuses:
* ComputeListener is responsible for reporting the Accepted and Programmed conditions for the Listener.
* If a Listener is reported as not Accepted, it should also be not Programmed.
* If and only if the Listener returned from ComputeListener is nil or deson't contain a filter chain (call this a "valid listener"), the Programmed status for the listener should have been reported aso False, as it will not be included in the data plane.

While iterating over the Listeners, Translate is checking if a valid listener is returned before adding the tranlated Envoy listener to the output. We will add additional status processing to logic as well:

* Per Invalid listener
  * Validate that the Programmed condition has been reported, and report it as False if it has not.
  * Check the Accepted condition
  * Track names listeners that are not Accepted and not Progammed in separate lists

* After All Listeners
  * Check for listeners not Accepted
    * If ALL listeners are not Accepted, set the Gateway Accepted condition to false with the reason ListenersNotValid and a message listing the non-Accepted listeners
    * ElseIf ANY listeners are not Accepted, set the Gateway Accepted condition to true with the reason ListenersNotValid and a message listing the non-Accepted listeners
  * Check for listeners not programmed
    * If ALL listeners are not Programmed, set the Gateway Programmed condition to false with the reason ListenersNotValid and a message listing the non-Programmed listeners
    * ElseIf ANY listeners are not Programmed, set the Gateway Programmed condition to true with the reason ListenersNotValid and a message listing the non-Programmed listeners
